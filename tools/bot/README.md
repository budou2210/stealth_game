# 攻略ボット

難易度「地獄」をクリアできることを確かめ、クリアの様子を見るための自動プレイです。
ゲームの状態をコピーして先の展開をシミュレーションする「未来予知」を使っています（人間には同じことはできません）。

できること：

- 地獄に挑戦し、クリアできた回の入力を記録する（32配置中、27〜31配置をクリア）
- 記録を本物のゲーム画面で再生する
- 速いクリアの記録の後半をやり直して、さらに縮める
- 速さを詰める動き（`--fast`）で、より速いクリアを探す（これまでの最速は 45.63秒。下の「速さを詰める（--fast）」）
- 難易度「超越」にも挑戦できる（`--level transcend`。下の「超越で動かす」）。クリアできるのは32配置中2配置ほど

コマンドはすべて、プロジェクトのフォルダで実行します。PowerShell でもコマンドプロンプトでも動きます（書き方が違うのは、下の「切り替えスイッチ」の設定だけです）。

## コマンド一覧

### 1. 挑戦する（run）

```
uv run python -m tools.bot.run --attempts 8
```

| オプション | 意味 | 初期値 |
|---|---|---|
| `--attempts` | 挑戦する配置の数 | 10 |
| `--workers` | 同時に動かす数（PCのコア数まで） | 8 |
| `--variants` | 同じ配置を、動きを少し変えてさらに何通り試すか（一番速いクリアを残す。計算は 1+この数 倍） | 0 |
| `--max-minutes` | 1回の挑戦の計算時間の上限（分）。超えたら打ち切る | 15 |
| `--seed` | 配置を1つに決める（選び分けをしない） | なし |
| `--level` | 遊ぶ難易度（`hell`＝地獄、`transcend`＝超越） | hell |
| `--fast` | 速さを詰める動きで試す（下の「速さを詰める（--fast）」）。結果は `bot_results/<難易度>_fast` に分ける | なし |
| `--results` | 結果を保存するフォルダ | `bot_results/<難易度>`（地獄は `bot_results/hell`、超越は `bot_results/transcend`） |

注意：

- `--seed` で配置を決めると、`--attempts` の回数だけ同じ配置に挑戦します。1回でよいときは `--attempts 1` にしてください。
- 配置は、これまでの結果から作った「危険度の地図」をもとに、有望なものから選びます。実行するたびに地図が更新されます。
- 1回の挑戦は、多くが1〜3分です。行き詰まった回は、打ち切り（15分）まで続きます。

### 2. 記録の後半をやり直して縮める（refine）

```
uv run python -m tools.bot.refine --seed 2214
```

クリアの記録を途中まで再生し、そこから動きを変えて残りをやり直します。
戻る時点は、記録の終わりから5秒ずつ前の8か所です。
速くなったら記録を書き換え、新しい記録からもう一度くり返します。

| オプション | 意味 | 初期値 |
|---|---|---|
| `--seed` | やり直す記録の種（`bot_results/<難易度>/wins/seed_<種>.json`）。必須 | なし |
| `--rounds` | 速くなったときに、くり返す回数の上限 | 3 |
| `--variants` | 1つの時点から試す動きの数 | 4 |
| `--workers` | 同時に動かす数 | 8 |
| `--fast` | 速さを詰める動きでやり直す（`bot_results/<難易度>_fast` の記録を読む・書く） | なし |
| `--results` | 結果のフォルダ | `bot_results/<難易度>` |

- 書き換える前の記録は、初回だけ `seed_<種>.orig.json` として残します。
- 新しい記録は、最初から再生して同じ結果になることを確かめてから保存します。
- 1つの記録で2〜13分ほどかかり、元の記録から約1割縮みます（例：2214 は 70.83秒 → 62.3秒）。

### 3. 再生する（play_record）

```
uv run python -m tools.bot.play_record bot_results/hell/wins/seed_2214.json
```

| オプション | 意味 |
|---|---|
| `--speed 2` | 2倍速で再生する |

- 再生中のキー：Tab（視点）・F（足音の範囲）・P（一時停止）・R（最初から再生し直す）・Esc（終了）。
- M（難易度選択）は使えません。クリアしても、ベストタイムには記録されません。
- `bot_results/<難易度>/runs/` の記録（クリアできなかった回）も再生できます。どこで失敗したかを見るのに使えます。

### 4. 切り替えスイッチ（BOT_OPTIONS）

試験用の動き方です。コマンドの前に、別の行で設定します。使っているウィンドウによって書き方が違います
（行の頭が `PS C:\...>` なら PowerShell、`C:\...>` だけならコマンドプロンプトです）。

| | 設定する（例：V） | 元に戻す |
|---|---|---|
| PowerShell | `$env:BOT_OPTIONS="V"` | `$env:BOT_OPTIONS=""` |
| コマンドプロンプト | `set BOT_OPTIONS=V` | `set BOT_OPTIONS=` |

設定はそのウィンドウを閉じるまで残ります。

| 記号 | 内容 | 試験の結果 |
|---|---|---|
| V | 速度重視：足音を気にせず、見られない限り走る | 最速は出やすい（58.83秒）が、平均は悪くなる（120秒 → 190秒） |
| T | 1区切りを約0.47秒に短くして、忍び足の速さを無駄なく使う | 速くなる配置と遅くなる配置があり、平均は変わらない |
| A | 配置を選ぶとき、アイテムを回る道のりが短い配置を優先する | 道のりが短い配置は危ない場所にアイテムがあり、効果なし |
| C | 同じくらい近づけるなら、早く着く経路を選ぶ | 遅くなる |
| D | アイテムを集める順番を、道のりが短くなるように組み替える | 変わらない |
| S2 | 滑らかに動くとき、2区切り先まで近道する | 予定とずれやすい |

`--fast` の試験で足したスイッチ（F1〜F9）は、下の「速さを詰める（--fast）」にまとめています。

複数使うときは `V,T` のようにカンマで区切ります（PowerShell なら `$env:BOT_OPTIONS="V,T"`、コマンドプロンプトなら `set BOT_OPTIONS=V,T`）。

## 目的ごとのおすすめ

### 平均値（多くの配置で、安定して速くクリアする）

```
uv run python -m tools.bot.run --attempts 8 --variants 3
```

- スイッチは付けません。
- 32配置の試験では、`--variants` なしと比べて、クリア 27 → 31、平均 134.5秒 → 113.7秒でした。
- 計算は4倍かかります（8配置で40分ほど）。

### 最大値（一番速い1回を狙う）

1. 配置をたくさん回して、速いクリアの元を集めます（16配置で30分ほど）。

   ```
   uv run python -m tools.bot.run --attempts 16
   ```

2. 速かった上位3つほどを、それぞれやり直して縮めます。速い記録の種は `bot_results/hell/attempts.jsonl` の `time` が小さい行で分かります。

   ```
   uv run python -m tools.bot.refine --seed 2214
   ```

3. 一番速い記録を、速度重視でさらにやり直します（例：2214 は 62.3秒 → 60.5秒）。

   ```
   $env:BOT_OPTIONS="V"
   uv run python -m tools.bot.refine --seed 2214
   ```

   コマンドプロンプトでは、1行目を `set BOT_OPTIONS=V` にします。

### 速さを詰める（--fast）

run と refine に `--fast` を付けると、試験で効果があった工夫をまとめて使います。
結果は `bot_results/hell_fast/` に、ふだんの結果（`bot_results/hell/`）とは別に残ります。
危険度の地図も別ですが、最初の1回だけは、ふだんの結果の地図から始めます。
付けなければ、地獄のボットは今までどおり（51.13秒の記録を出したときと同じ動き）です。

```
uv run python -m tools.bot.run --attempts 16 --fast
uv run python -m tools.bot.refine --seed <種> --fast
uv run python -m tools.bot.play_record bot_results/hell_fast/wins/seed_<種>.json
```

- run は、1つの配置を「アイテムの順番を全部比べて決める」「近い順に決める」の2通りで試し、速いほうを残します（配置によって、どちらが速いかが違うため）。計算は約1.7倍かかります。
- refine は、やり直す時点が多くなる（2.5秒ごとの16か所と、アイテムを拾った直後）ので、計算は約3倍かかります。

32配置・上限15分での試験の結果（2026-11-07）：

| | クリア | 平均 | 中央値 | 最速 |
|---|---|---|---|---|
| ふだんの動き | 27/32 | 154.1秒 | 137.7秒 | 57.23秒 |
| `--fast` | 31/32 | 133.2秒 | 111.5秒 | 46.10秒 |

種410 の記録は、run で 46.07秒、refine（`--fast` と同じやり直し方）で 45.63秒になりました（今までの最速 51.13秒より速い）。

試した工夫と結果（スイッチの記号は BOT_OPTIONS で1つずつ試せます。`--fast` で使うのは ○ のもの）：

| 記号 | 内容 | 結果 | --fast |
|---|---|---|---|
| F1 | アイテムの順番を、全部の順番を比べて一番短いものにする | 32/32 クリア・最速 46.07秒。ただし配置によっては遅くなる | ○（使う・使わないの両方で試す） |
| F2 | 走るときに斜め・桂馬の動きも使う | 遅くなる | |
| F3 | 同じくらい近づけるなら走る。足音の余裕を小さく | 遅くなる | |
| F4 | 目標に届く経路のうち、一番早く届くものを選ぶ | F1 と合わせると、全部クリアのまま速くなる | ○ |
| F5 | refine のやり直す時点を細かく（2.5秒ごと・16か所＋アイテムを拾った直後） | 410 で 46.07 → 45.63秒（今のやり方では縮まず）。1329 は縮まず | ○ |
| F6 | 何度も見つかる場所を避ける（超越用の工夫） | 遅くなる | |
| F7 | 視界の余裕をさらに小さく（距離0.3→0.15、角度5°→3°） | タイムは一番縮む（同じ配置で 153→141秒）が、クリアが減る | ○ |
| F8 | 確かめで経路がだめなら、別の経路を探し直す | 遅くなる | |
| F9 | 危険度の重みを小さく（6→3、6→1.5） | クリアは増えるが遅くなる | |

### 超越で動かす

run と refine に `--level transcend` を付けます。結果（危険度の地図・記録）は `bot_results/transcend/` に、地獄（`bot_results/hell/`）とは別に残ります。
記録には難易度が入っているので、play_record は付けなくてもその難易度で再生します。

```
uv run python -m tools.bot.run --level transcend --attempts 16
uv run python -m tools.bot.refine --level transcend --seed <種>
uv run python -m tools.bot.play_record bot_results/transcend/wins/seed_<種>.json
```

超越では、ボットは監視カメラに映ること・閉まった扉のマスにいることも「見つかる」と同じに扱って避けます。
鳴る床は避けませんが、音で近くの鬼が調べに来るような動きは、実行前の確かめで取りやめます。

超越では、地獄にはない次の3つの工夫も使います（地獄で使うとクリアが減ったので、地獄では使いません。
地獄のボットは、51.13秒の記録を出したときと同じ動き方のままです）。

| 工夫 | 中身 |
|---|---|
| 予測の使い回し | 約1秒ごとに作る12秒先の予測のうち、まだ先にある11秒ぶんを使い回す |
| 視界の計算の丸め | 鬼の位置を0.1マス、向きを3°単位に丸めて、計算した視界を覚えて使い回す |
| 何度も見つかる場所を避ける | 直近8回の失敗のうち、2マス以内で2回以上見つかった場所の周りには入らない |

同じ16配置・上限20分で比べると、超越のクリアは 0 → 2 配置に増えました（2026-11-06）。

### タイムアタックで動かす（time_attack）

鬼がいないので、「8個のアイテムを集めて出口へ行く一番速い順番と道」を計算するだけの別のボットです。
道・順番・動かし方の中心部分はゲーム本体の `src/stealth_game/ghost.py` にあり、ゲームの中でタイムアタックのリプレイに重ねる「ゴースト」と同じものです。
このコマンドは、それに「仕上げ」（入力を少しずつ変えて縮める）を足したものです。ゲームの中のゴーストは、待ち時間を短くするため候補を5本に絞り、仕上げもしません。

```
uv run python -m tools.bot.time_attack --seeds 0-99
```

| オプション | 意味 | 初期値 |
|---|---|---|
| `--seed` / `--seeds` | 解く配置の種（`--seeds 0-99` や `1,5,9`） | 0 |
| `--candidates` | 実際に動かして比べる順番の数の上限 | 10 |
| `--margin` | 最短の距離から何割増しまでの順番を候補にするか | 0.08 |
| `--refine-seconds` | 仕上げ（入力を少しずつ変えて縮める）に使う秒数。0でしない | 3 |
| `--exact-samples` | 選んだ順番の最短の道を求めるときの、円の周の候補の数（多いほど保証の幅が小さく、遅い）。0でしない | 360 |
| `--cutoff` | 足切りの秒数。厳密な下限がこれ以上の配置は計算しない（通った配置は最後まで計算する）。0で足切りしない | 22.7 |
| `--results` | 結果のフォルダ | `bot_results/time_attack` |

- クリアの記録は `bot_results/time_attack/wins/seed_<種>.json`。`play_record` でそのまま再生できます。
- 同じ種の記録は、前より速いとき、または同じタイムでキーの切り替えが少ないときだけ書き換えます。
- 記録は最後に「斜めとまっすぐの細かい切り替えをまとめる」並べ替え（`ghost.smooth_log`）をかけます。斜めとまっすぐは、混ぜて進んでもまとめて進んでも、着く場所とかかるコマ数が同じなので、タイムは変わりません。区間ごとに、並べ替えの前後で区間の終わりの位置・拾ったアイテムが同じになるときだけ採り、壁に当たる区間は半分に分けて試します。最後に本物と同じ処理で流し直して確かめます（約0.04秒。ゲーム内のゴーストも同じ並べ替えをかけます）。種861では、キーの切り替えが287回 → 61回になりました。
- 足切りで落ちる配置は約0.01秒、通った配置は仕上げなどを含めて約8秒です（200配置で約2分）。
- 結果には「下限」（どの順番でどう動かしても、これより速くはできない時間）も出ます。

しくみと、計算量を減らす工夫：

| 段階 | そのまま計算すると | 工夫 |
|---|---|---|
| 距離と道 | 細かいマス目（0.1マス刻みで約16万点）で最短の道を探す | 体が通れる場所の「出っ張った角」（232個）だけを中継点にした地図（可視グラフ、`src/stealth_game/route_graph.py`）で、壁ぎりぎりの本当の最短の道を引く。地図は全部の配置で同じなので1回だけ作る（約0.04秒）。角に沿わない向きのつながりは、見通しを調べる前に捨てる |
| 順番 | 8! = 40320 通り × 9区間 ≈ 36万回 | 動的計画法（Held-Karp）で 2^8 × 8 × 8 ≈ 1.6万回 |
| 候補 | 全部の順番を動かして比べる | 動的計画法の表で「ここから先の最短」が正確に分かるので、最短の少し上までの順番だけを、無駄な枝をたどらずに挙げる |
| 触れる点 | アイテムの中心まで行く | アイテムは0.7、出口は0.9まで近づけば十分なので、その円の上で「前後の点からの距離の合計」が一番短い点を選ぶ |
| 動かす | 次のマスばかりを目指す | 8方向のうち一番近づく向きを1コマごとに選び、先の点が見通せたら手前の角を飛ばす。今までの最速を超えたら打ち切る |
| 仕上げ | ― | 入力のコマを入れ替える・逆向きの2コマを抜く・1コマ抜くを試し、速くなれば採る（ずれが後に残りにくい変え方だけ） |

道を引くときは体を0.04だけ大きく見ます（斜めとまっすぐを混ぜて進むと線から少し揺れるため。0.02〜0.12で比べて一番速かった大きさ）。

種0〜9の平均（2026-11-08）：前のやり方（マスの中心をたどる）28.61秒 → 今のやり方 28.15秒。

#### 選んだ順番での本当の最短（`src/stealth_game/exact_route.py`）

一番速かった順番について、触れる点の選び方まで含めた本当の最短の道を、保証の幅つきで求めます（1配置 約3秒）。

| 手順 | 中身 |
|---|---|
| 地図 | 体の本当の大きさ（0.3）、角の中継点をほぼ壁に付けた地図。0.05マス刻みのマス目の計算と8組で比べ、マス目より長くなることはなかった（マス目は本当の最短以上なので、この地図は最短を取りこぼしていない） |
| 触れる点 | 道は円の外から入るので、触れる点は円の周の上。周に360点を並べ、壁で周が切れるところは切れ目の点も必ず入れる |
| つなぎ方 | 「スタート → 1個目の候補 → … → 出口の候補」の一番短いつながりを、前から順に表を埋めて求める（候補の組み合わせを全部比べたのと同じ結果になることを、テストで確かめている） |
| 保証の幅 | 本当の最短の道が触れる点のそばには、同じ弧の上、間隔の半分以内に候補がある。弧に沿って回り込めば乗り換えられるので、「求めた長さ − 本当の最短 ≤ 保証の幅」（360点で約0.11、1コマ分 0.153 より小さい） |

結果には「この順番の最短の道の長さ」と「この順番でのクリアのコマ数の下限」（どう動かしても、これより少ないコマではクリアできない）が出ます。

ゲームの当たり判定は、斜めの1コマを「横に動く → 縦に動く」として行き先だけを調べるので、斜めのまっすぐな線は壁の角を最大0.05ほどかすめられます。そのため下限は、体の大きさを0.245（0.3 − 斜めの1コマの半分）と見た地図で測ります（1コマの線の途中の点は、前後の位置から縦横0.055以内にあるので、この大きさなら必ず通れる。テストで確かめている）。最短の道（ボットが目指す道）は、体の大きさ0.3のままです。

種0〜9では、ボットの記録は「体の大きさ0.3での最短の道」の長さより11〜23コマ（0.4〜0.8秒）多くなりました。最短の道の触れる点で動かし直してもほとんど縮まないので、残りは道ではなく動かし方の損（壁から0.04離して進む余裕・斜めとまっすぐを混ぜる揺れ）と見ています。
保証するのは「選んだ順番の中での最短」で、順番そのものの最短（ほかの順番のほうが速い可能性）は含みません。
順番は「計画した順番」ではなく「ボットが実際に拾った順番」で測ります。計画どおりに向かっても、途中で別のアイテムのそばを通って先に拾うことがあるためです
（例：種104は計画では5→0だが、実際は0→5。計画した順番の下限は691コマ、実際の順番の下限は655コマで、ボットは681コマ）。
この例を受けて、順番の選び方も改善しました（下の「順番の選び方」）。

#### 順番の選び方

中心どうしの距離で選んだ候補（最短の8%増しまで、10本）に加えて、中心どうしの距離で最短の25%増しまでの順番（最大1000本）を
「円に触れればよい」前提の長さ（`exact_route.OrderScorer`。円の周の候補を24点に絞り、候補の点と見える角はアイテムごとに使い回すので、1本数ミリ秒）で比べ、
短い10本も一緒に動かして比べます。足切りを通った配置で約2秒増えます。

足切りを通る種0〜199の11配置で比べると、縮んだのは2配置（2コマずつ）だけで、平均は23.936秒 → 23.924秒でした（2026-11-08）。
種104の差は、計画どおりには進まず、偶然もっと良い順番で拾えていたためで、順番の選び方の余地は小さいと分かりました。
ボットと「この順番の下限」の差（約20コマ）のほとんどは、順番ではなく動かし方の損です。

#### 動かし方の改善（試したこと）

選んだ順番の最短の道の触れる点で、次の2通りの動かし方も試し、速ければ採ります（足切りを通った配置で約2秒増えます）。

| 動かし方 | 中身 |
|---|---|
| `drive_through` | 今までと同じ動かし方で、触れる点だけ最短の道のものを使う |
| `drive_touches` | 1コマごとに、8方向それぞれについて「動いた先から最後までの残りの長さ」（次の触れる点までの地図の上の最短距離＋その先の触れる点どうしの距離）を求め、一番短くなる向きを選ぶ。どの向きでも縮まないときは、2手先・3手先まで試す |

種0〜199で足切りを通る11配置では、平均 23.91秒 → 23.90秒（縮んだのは2配置・1コマずつ）でした（2026-11-08）。

分かったこと：
- 体の本当の大きさ（0.3）の地図で残りの長さを測ると、道が壁にぴったり沿うため、壁際でつかえて進めなくなる配置が多い
  （1コマ0.153ずつ飛び飛びにしか動けず、行き先が壁なら1コマの移動がまるごと取り消されるため）。体を0.04大きく見た地図で測ると、つかえなくなる。
- ボットと下限の差（約20コマ）は、曲がり角での切り替えの損より、「飛び飛びにしか動けないので、壁際の最短の線にぴったり乗れない」損が大部分と見ている。
  これを縮めるには、1コマ単位の入力の探索が要る。

#### 足切り（`--cutoff`）

はじめに、どの順番でどう動かしても越えられない厳密な下限（`exact_route.strict_lower_bound`、約0.01秒）を出し、これが足切りの秒数以上なら、その配置はそこで終わりにします。下限は、中心どうしの最短距離から「中心から円の周までの最大の距離」（壁がかかる円では回り道も入れて測る）を引き、一番短い順番を動的計画法で求めたものです。

初期値22.7秒は、上位5〜10%の配置が残るように決めました（2026-11-08。はじめは上位20〜30%の24.5秒にしていた）。
はじめは「動かした結果が足切り以上なら仕上げなどを省く」段階もありましたが、足切りを強くすると、通った配置もほとんど仕上げられなくなるのでやめました。

| 足切り | 残る配置（種0〜1999の厳密な下限） |
|---|---|
| 22.2秒 | 5.0% |
| 22.7秒 | 7.5% |
| 23.0秒 | 9.0% |
| 24.0秒 | 17.7% |
| 24.5秒 | 24.3% |
| 25.0秒 | 32.1% |

ボットのタイムも測った種0〜199では、下限とボットのタイムの差は1.5〜3.3秒（中央 2.1秒）でした。22.7秒の足切りでは、ボットのタイムで上位10配置（上位5%）は全部残り、上位20配置のうち11配置が残りました（足切りの下限は厳密なので、22.7秒より速くクリアできる配置は、そもそも落ちません）。

## 記録を探す（PowerShell）

結果のファイルから、速い記録などを探すコマンドです。どれも **PowerShell** で、プロジェクトのフォルダで実行します
（コマンドプロンプトのときは、先に `powershell` と打ってから入力します）。
例は地獄（`bot_results\hell`）です。超越を見るときは、`hell` を `transcend` に変えます。

### いちばん速い記録（今の最速。再生できる記録と同じタイム）

```
Get-ChildItem bot_results\hell\wins\seed_*.json -Exclude *.orig.json | ForEach-Object { $j = Get-Content $_ | ConvertFrom-Json; [pscustomobject]@{seed=$j.seed; time=$j.time; refined=$j.refined} } | Sort-Object time | Select-Object -First 10
```

`refined` に数字があれば、refine で縮めた記録です（数字は何回目に縮んだか）。

### 挑戦の結果（attempts.jsonl）から探す

`attempts.jsonl` には、run の挑戦が1回ずつ全部残っています（遅い回も残ります。refine の結果は入りません）。

| 見たいもの | コマンド |
|---|---|
| クリアを速い順に10件 | `Get-Content bot_results\hell\attempts.jsonl \| ConvertFrom-Json \| Where-Object outcome -eq "win" \| Sort-Object time \| Select-Object -First 10 seed,time,rewinds` |
| 結果ごとの数（win・lose・stuck・time_limit） | `Get-Content bot_results\hell\attempts.jsonl \| ConvertFrom-Json \| Group-Object outcome \| Select-Object Name,Count` |
| 1つの種の挑戦を全部（例：1329） | `Get-Content bot_results\hell\attempts.jsonl \| ConvertFrom-Json \| Where-Object seed -eq 1329 \| Select-Object seed,outcome,time,items,rewinds,variant` |
| 最近の挑戦10件 | `Get-Content bot_results\hell\attempts.jsonl -Tail 10 \| ConvertFrom-Json \| Select-Object seed,outcome,time,items,rewinds` |

（README をメモ帳などでそのまま開いた場合、表の中のコマンドは `\|` と書いてありますが、実際には `|` と打ちます。GitHub で見ると `|` と表示されます）

### その他

| 見たいもの | コマンド |
|---|---|
| refine で縮めた記録だけ | `Get-ChildItem bot_results\hell\wins\seed_*.json -Exclude *.orig.json \| ForEach-Object { Get-Content $_ \| ConvertFrom-Json } \| Where-Object refined \| Sort-Object time \| Select-Object seed,time,refined` |
| クリアの記録の数 | `(Get-ChildItem bot_results\hell\wins\seed_*.json -Exclude *.orig.json).Count` |

### 並べ方・件数の変え方

| 変えたいこと | 変えるところ |
|---|---|
| 遅い順にする | `Sort-Object time` を `Sort-Object time -Descending` にする |
| 件数を変える | `-First 10` の数字を変える（全部表示するなら `-First 10` を消す） |
| 表示する項目を変える | `Select-Object` の後ろの名前を変える（`seed` `outcome` `time` `items` `rewinds` `variant` `layout_score` `compute_seconds` など） |

## 結果のファイル

`bot_results/<難易度>/`（地獄は `hell`、超越は `transcend`）に保存します（GitHub には上げません）。

| ファイル | 内容 |
|---|---|
| `attempts.jsonl` | 挑戦ごとの結果（1行に1回） |
| `danger.json` | 危険度の地図（次の実行はここから続ける） |
| `wins/seed_<種>.json` | クリアできた回の入力の記録。同じ種で何度もクリアしたら、一番速い回を残す |
| `wins/seed_<種>.orig.json` | refine で書き換える前の記録 |
| `runs/seed_<種>.json` | クリアできなかった回の入力の記録 |
| `errors.log` | 挑戦の途中でエラーが起きたときの内容（その挑戦だけ飛ばして、ほかは続ける） |

## しくみ

| ファイル | 役割 |
|---|---|
| `sim.py` | 画面なしのシミュレーター。ゲーム本体の処理を借りて、本物と同じ動きをする。状態をまるごとコピーできる |
| `spacetime.py` | 時間と場所の経路探索。警備員の動きを12秒先まで予測し、0.5秒ごとに「見つからないマス」だけをたどる |
| `planner.py` | 判断の中心。経路を本物どおりに試してから動く。捕まったら5秒ごとの保存点へ巻き戻してやり直す |
| `danger.py` | 危険度の地図と、配置の選び分け |
| `run.py` | 挑戦をくり返し、結果を保存する |
| `refine.py` | 記録の後半をやり直して縮める |
| `play_record.py` | 記録を本物のゲーム画面で再生する |
| `worker.py` | 挑戦を別のプロセスで動かす（同時に走らせるため） |
| `options.py` | 切り替えスイッチ |
| `levels.py` | 遊ぶ難易度（`--level`）と、結果のフォルダの場所 |

主な工夫：

- 動く前に、その入力で本当に見つからないか、その後4秒は逃げ続けられるかをシミュレーションで確かめる
- 最後のアイテムは、拾ってから出口まで逃げ切れると分かったときだけ取りに行く
- 近くに警備員がいなければ走る
- マスの中心で止まらず、斜めに近道して滑らかに動く
- 見つかる距離・足音の距離にとる余裕を小さめにして、積極的に動く
